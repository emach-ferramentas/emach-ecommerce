# Deploy via repo espelhado (org) e gates de CI: build, drift-check de env e test:ci unit-only

O código é trabalhado no repo **canônico** `othavi0/emach-ecommerce` (onde o GitHub Actions roda). A Vercel está conectada a `emach-ferramentas/emach-ecommerce` (repo da org). O espelho recebe os workflows e tem Actions ligado, mas todo job só roda no canônico por guarda de repositório e sai `skipped` no espelho; X vermelho lá não indica `main` quebrada, porque o sinal é o CI do canônico. Um workflow de mirror (`.github/workflows/mirror.yml`) no canônico espelha a `main` pro repo da org depois que o CI da `main` termina verde (`workflow_run`), e é esse push que dispara o deploy. O CI tem três jobs: `check-types` (lint, tipos e testes unit, sem banco), **`build`** (`next build` contra um Postgres descartável do job) e **`check-env`** (drift de env vars vs Vercel). A sequência exata de passos vive no `ci.yml`.

## Considered Options

- **Apontar a Vercel direto pro repo pessoal:** rejeitado — elimina os 2 repos, mas desconecta o código do repo da org (`emach-ferramentas`), que é a referência oficial da empresa. Mantido o mirror para preservar ambos.
- **Mirror manual (push cross-account a cada deploy):** rejeitado — atrito a cada deploy; fácil esquecer e o deploy ficar num commit velho (foi exatamente como o build quebrou com `NEXT_PUBLIC_SITE_URL` faltando).
- **Validar env só no build da Vercel (status quo do t3-env):** rejeitado — `@emach/env` valida tarde (no `next build`), então env obrigatória faltando só estoura no deploy. O `check-env` move o gate pra antes, no CI.
- **Mirror em todo push, sem esperar o CI:** era a decisão original. Rejeitado depois: `main` vermelha deployava, e erro de prerender (`cacheComponents`, `generateStaticParams`) só aparecia como build falho calado na Vercel, com a produção presa no último deploy bom.
- **Build do CI contra o Supabase compartilhado:** rejeitado — o banco é dev=prod e o CI não recebe segredo de banco. O job `build` sobe Postgres, aplica schema, triggers, categorias e a fixture `.github/ci/build-fixture.sql`, e usa env dummy de `scripts/dummy-env.ts`.
- **Rodar testes de integração no CI:** rejeitado — batem no Supabase compartilhado e são flaky sob concorrência (ver ADR e CLAUDE.md). Ficam fora via `VITEST_UNIT_ONLY=1`.

## Consequences

- **Deploy = merge na `main` com CI verde.** O mirror propaga pro `emach-ferramentas` e a Vercel deploya. Sem push manual. O mirror pula o commit que o repo da org já tem; o push sem force nunca volta a produção para trás, e um commit verde vai ao ar mesmo que o seguinte esteja com o CI vermelho.
- **Mirror (`mirror.yml`) exige `MIRROR_TOKEN`** = PAT fine-grained da conta `emach-ferramentas` (permissões `Contents` R/W + `Workflows` R/W). É o mesmo PAT do mirror do dashboard, com escopo nos dois repos de deploy (`emach-dashboard` e `emach-ecommerce`), como diz o `mirror.yml` do dashboard. Cadastrado como secret no canônico. Dois gotchas que custaram tempo:
  - **`actions/checkout` precisa de `persist-credentials: false`** — senão grava um `http.extraheader` com o `GITHUB_TOKEN` do repo, que tem precedência sobre o `MIRROR_TOKEN` da URL e dá `permission denied` no destino (sintoma confuso: o PAT funciona local mas falha no CI).
  - **Cadastrar o secret com `gh secret set --body "$VALUE"`, nunca via pipe** (`printf | gh secret set` corrompeu o valor → `HTTP 401`).
- **Drift-check (`bun check:env`, `scripts/check-vercel-env.ts`)** deriva as env vars obrigatórias do próprio Zod (`packages/env/src/schemas.ts`, via `safeParse(undefined)`) e cruza com a API da Vercel — à prova de futuro (env obrigatória nova é coberta sem editar o script). Secrets `VERCEL_TOKEN`/`VERCEL_ORG_ID`/`VERCEL_PROJECT_ID` vivem no **canônico** (onde o CI roda); sem `VERCEL_TOKEN` o job falha em push na `main` e pula com warning em PR (fork não recebe secrets); com o token e sem `VERCEL_ORG_ID`/`VERCEL_PROJECT_ID`, o `check-env` falha. **Env var obrigatória nova precisa ser cadastrada na Vercel** (`vercel env add`) — senão o `check-env` falha no CI e o build falharia no deploy. Exceção: `UPSTASH_REDIS_REST_URL` e `UPSTASH_REDIS_REST_TOKEN` são opcionais no Zod (dev usa fallback em memória) mas obrigatórias no deploy; o script as exige por uma lista fixa (`REQUIRED_IN_PRODUCTION`). Sem elas, o cache Frenet e os rate limiters degradam em silêncio para memória por instância.
- **`test:ci` é unit-only.** As regras (sufixo `.integration.test.ts`, guarda, env dummy) estão no `CLAUDE.md`, seção Deploy e CI.
- **O que trava o deploy sem erro no mirror.** Commit com `[skip ci]` (ou push feito pelo `GITHUB_TOKEN`) não roda o CI e não deploya até o próximo commit verde, que o leva junto. `VERCEL_TOKEN` vencido ou a API da Vercel fora do ar derrubam o `check-env` e travam todo deploy. A saída nos dois casos é o `workflow_dispatch` do mirror, disparado na `main`, que empurra a ponta dela.
- **O build do CI sobe o schema num `postgres:17` puro.** Se um PR de sync do dashboard trouxer algo exclusivo do Supabase (role `anon`/`authenticated`, extensão, FK para `auth` ou `storage`), o job `build` quebra e trava o deploy. A troca seria a imagem `supabase/postgres`.
- **Todo job de `.github/workflows/` leva `if: github.repository == 'othavi0/emach-ecommerce'`.** O espelho recebe os workflows com o código e tem Actions ligado, mas não tem os secrets: sem a guarda, o CI falha lá a cada push espelhado. No `mirror.yml` a guarda vem antes da condição do evento, com o resto entre parênteses. `scripts/workflows.test.ts` (no `test:repo`) falha se um job, atual ou novo, nascer sem ela.
- **PAT tem validade/escopo** — quando rotacionar, atualizar o secret `MIRROR_TOKEN` (`gh secret set ... --body`).
